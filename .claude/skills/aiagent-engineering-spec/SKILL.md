# AI agent应用开发规范

一、规范目标与核心原则
1.1 规范目标

本规范用于指导 AI 辅助软件工程和 AI Agent 工程的完整生命周期，使开发过程具备：

可行性：确认 AI、LLM、Agent 或传统技术是否适合解决目标问题。
可控性：根据工程规模、风险和用户偏好选择合适的治理流程。
可验证性：每项交付都有明确的完成定义和适用的验收证据。
可追溯性：重要决策、代码变更、测试结果和审批记录可查询。
可恢复性：发生缺陷、失败、成本超限或部署问题时，有明确的恢复方案。
可维护性：考虑后续运行成本、模型变更、依赖升级和技术债务。
高效率：避免无意义拆分、重复汇报、过度设计和不必要的审批。

本规范包含一个工程启动配置阶段（Gate 0）和十二个治理关卡（Gate 1–12）。

Gate 0 用于确定本工程需要采用的流程；Gate 1–12 根据选定配置、实际风险和触发条件执行。

1.2 五项基本原则

原则一：按需治理，而非机械执行。

治理深度取决于工程主题、工作量、复杂度、依赖、风险及用户选择。小工程不必自动执行所有流程，大工程也不必为了形式而拆分过细。

原则二：流程可选，但安全底线不可随意关闭。

普通文档、重复报告等流程可以简化或关闭。涉及未授权的高风险操作、敏感数据、不可逆副作用或必须人工批准的事项时，必须保留对应的安全门禁。

原则三：依赖关系优先于关卡编号。

关卡具有逻辑上的推荐顺序，但不要求所有活动严格串行。无依赖关系的工作可以并行推进；需要前置结论的工作不得在缺少有效结论时直接实施。

原则四：状态必须反映真实情况。

不得将计划写成已完成、将代码测试通过写成集成通过、将合并写成部署成功，或将回滚方案写成已验证回滚。

原则五：发现问题后允许回退、修订和重新规划。

如果新证据推翻了原有假设，应重新评估受影响的部分，而不是机械地从头执行全部流程。

1.3 规范适用范围

本规范适用于：

AI Agent、单 Agent、多 Agent 和工具调用工作流。
LLM、RAG、Prompt、模型评测及数据处理流水线。
普通软件功能、API、自动化脚本和 AI 与传统代码混合系统。
技术方案评估、工程任务拆解、分支开发和集成。
工期、成本、测试、生产部署和运行维护。
工程日志、备份、回滚及项目关闭。

如果任务只是简单问答、纯文本润色或不涉及工程实施的讨论，不需要自动启动完整的工程治理流程。

二、Gate 0：工程启动前的治理流程配置
2.1 目标

在正式实施前，确定本次工程需要执行哪些治理流程、各流程的执行深度、汇报频率和审批要求。

配置应综合考虑：

任务主题与业务目标。
预计工作量及日历工期。
技术不确定性。
模块数量与依赖复杂度。
数据敏感性和安全影响。
失败后果与可逆性。
预算和持续维护成本。
用户对开发效率、文档、测试及汇报的偏好。

不要求用户手动填写所有配置。AI 应先根据现有信息给出推荐配置，只询问会实质影响方案的关键问题。

2.2 全局配置与局部配置
A. 全局配置

全局配置用于规定所有工程的默认治理策略，包括：

默认工程规模及风险分级规则。
各关卡的默认执行模式。
默认拆解粒度和分支策略。
默认进度汇报与完成报告频率。
默认测试和验收要求。
成本审批阈值。
强制安全和人工审批门禁。
允许采用的低风险例外。
日志、备份和回滚要求。

全局配置应有版本标识和生效范围。

全局配置发生变化时，不自动覆盖已经启动的工程。当前工程继续使用原配置，除非明确决定升级配置并记录影响。

B. 局部配置

局部配置仅对当前工程生效，可以：

启用或关闭允许自定义的关卡。
将完整流程调整为简化流程。
将常规执行调整为条件触发。
增加特定的测试、安全、成本或维护检查。
调整任务拆解粒度、分支方式和集成节点。
调整进度更新频率和报告详细程度。
为特定工程设置验收标准和里程碑。

局部配置可以比全局默认要求更严格，但不得关闭不可豁免的安全门禁，也不得扩大执行主体已经获得的权限。

2.3 关卡配置状态

每个关卡可以使用以下四种状态：

状态	含义	执行规则
ON	完整执行	输出该关卡规定的完整成果
LITE	简化执行	保留必要判断和证据，减少文档及重复操作
AUTO	条件触发	预先定义触发条件，满足时执行
OFF	关闭常规流程	不单独执行常规流程，但仍须满足强制门禁和依赖要求

OFF 不代表可以忽略风险。

关闭某个关卡前，必须检查：

是否有后续启用的关卡依赖其输出。
是否已有有效且仍适用的评估结果。
能否通过简化检查或已有证据补足必要输出。
是否存在不可豁免的安全或审批要求。

如果某关卡被关闭，但其必要输出被其他流程依赖，应采用以下方式之一：

使用仍然有效的既有结果。
执行该关卡的简化版本。
先完成最小必要检查。
调整后续工作，消除不必要的依赖。

不得因配置冲突而无限停滞。无法消除冲突时，应明确指出冲突项和最小解决方案。

2.4 十二关默认配置建议

以下是默认推荐，而不是所有工程必须采用的固定配置。

关卡	默认模式	主要适用场景
G1 可行性分析	ON / LITE	新 AI 任务、方案不明确时必须重点评估
G2 架构设计	ON / LITE	新系统、复杂功能或存在技术不确定性时
G3 工程拆解	按规模选择	多任务、跨模块或需要并行开发时
G4 分支与模块化	按风险选择	多人协作、多个单元或高风险代码修改时
G5 重大决策审批	AUTO	触发审批条件时必须执行
G6 统一交付汇报	按规模选择	存在独立交付单元时按约定触发
G7 分歧与阻塞处理	AUTO	发生阻塞、重大分歧或连续失败时
G8 工期与成本	按风险选择	多阶段工程、预算敏感或高成本任务时
G9 实施与验收	ON / LITE	代码或其他工程交付必须验证
G10 变更管理	AUTO	需求、接口、架构、预算等实质变化时
G11 维护与运行风险	按交付目标选择	生产系统、长期运行服务或高风险 Agent
G12 回滚与项目闭环	按风险选择	代码交付、生产变更、阶段交付或项目结束

G5、G7、G10 的条件触发配置必须保留必要的触发规则。即使关闭独立的常规报告，也不得绕过适用的审批和安全门禁。

G9 对所有实际工程交付都必须保留适用的验证；低风险任务可以简化测试范围，但不得将未经验证的结果标记为已验收。

2.5 工程启动配置记录

配置完成后，应形成简洁的工程配置记录：

工程名称和目标。
工程规模及风险等级。
全局配置版本。
局部关卡配置。
采用的架构和拆解深度。
验收要求。
汇报频率。
预算与审批阈值。
适用的安全门禁。
尚未确定的关键假设。
配置调整条件。

对于简单任务，可以只记录一句话的范围、验收方式和必要的风险检查，不强制生成完整配置表。

2.6 用户自定义流程

当用户希望自行选择关卡时，优先提供可直接修改的清单，而不是要求其填写大量表单。

示例：

G1 可行性分析：ON
G2 架构设计：LITE
G3 工程拆解：OFF
G4 分支与模块化：AUTO
G5 重大决策审批：AUTO
G6 统一交付汇报：LITE
G7 分歧与阻塞处理：AUTO
G8 工期与成本：OFF
G9 实施与验收：ON
G10 变更管理：AUTO
G11 维护与运行风险：LITE
G12 回滚与项目闭环：LITE

以上仅为配置示例，实际配置必须根据任务及风险确定。

用户可以选择“全部推荐”“轻量开发”“标准开发”“生产级开发”或“自定义”。AI 应说明推荐配置的关键取舍，并允许用户调整非强制选项。

三、工程规模与风险分级
3.1 工程规模
S 级：简单小工程

适用场景：

局部 Prompt、文案、配置或简单逻辑调整。
范围明确的独立缺陷修复。
小型工具函数或字段校验。
范围有限、可丢弃的实验。

推荐策略：

简要确认目标、实现方式和验收标准。
使用必要的轻量可行性判断。
不强制创建完整拆解表。
不强制独立分支，除非项目规则或风险要求使用。
只执行必要的测试和回滚检查。
开发中仅在出现阻塞、风险或需要决策时汇报。
完成后输出一次精简交付报告。
M 级：中型工程

适用场景：

新增独立 AI 功能或业务接口。
涉及多个文件、函数或少量模块。
需要 Prompt、解析、数据处理及测试共同配合。
需要一定的模型评测或集成验证。

推荐策略：

完成可行性和架构评估。
拆分可独立验证的工程单元。
明确主要接口、依赖、测试和分支策略。
在关键节点更新进度。
每个独立交付单元验收后形成统一记录。
在阶段结束时总结集成结果和遗留问题。
L 级：大型或高复杂度工程

适用场景：

多业务模块、多系统或多个外部服务。
复杂 Agent 工作流、RAG 系统或多阶段处理链路。
多人或多个执行单元并行开发。
涉及关键数据模型、权限、安全边界或生产系统。
技术不确定性较高，失败可能造成较大损失。

推荐策略：

完成适用的全部十二关治理评估。
建立项目级拆解表和里程碑。
使用独立分支及明确的接口契约。
按阶段进行验收和集成验证。
持续更新工期、成本和风险预测。
重要接口变更、重大风险和预算偏差及时报告。
项目结束时形成完整交付与闭环记录。

大型工程默认使用更完整的治理，但不意味着所有关卡都必须机械地重复执行。

3.2 风险等级独立于工程规模
风险等级	典型情况	治理要求
低风险	文档、局部逻辑、可逆的小改动	轻量检查、必要测试和记录
中风险	新功能、接口调整、模型切换	影响分析、测试、必要的集成验证
高风险	PII、生产迁移、权限扩大、不可逆操作	强制审批、安全检查和适用的回退保障

工程规模决定拆解深度和汇报频率；风险等级决定审批、验收和回退要求。

小型工程如果涉及生产数据库不可逆迁移，仍必须执行对应的高风险门禁。

3.3 动态重新分类

开发过程中，如果任务范围、工作量、依赖、技术不确定性或风险发生显著变化，应重新评估工程等级。

重新分类时：

保留已完成工作及有效验收记录。
识别新增风险和受影响的任务。
补充缺少的治理环节。
更新剩余工作、工期和成本。
对需要审批的事项执行审批。
继续推进不受变化影响的工作。

重新分类不意味着必须推翻全部已完成工作。

四、Gate 1：可行性分析（Task-Model Fit）
4.1 目标

判断应采用 LLM、传统代码、规则引擎、传统机器学习或混合方案。

4.2 评估维度

LLM 适配信号包括：

需要综合多源信息或理解自然语言上下文。
需要处理模糊语义、开放式输入或复杂文本。
可以通过评分标准约束一定的判断差异。
输出包括自然语言、分类标签、结构化提取或语义推理。
LLM 相比传统方案可能显著降低开发成本或扩大任务覆盖率。

风险信号包括：

核心结果要求严格确定性或可证明的数值准确性。
存在严格的延迟或吞吐量要求。
单次错误可能造成严重财务、法律、安全或生产损失。
必要知识无法可靠地通过上下文、检索、数据库或 API 提供。
隐私、成本或服务依赖无法满足业务要求。

出现风险信号时，先判断能否通过确定性代码、规则校验、权限限制、人工复核或其他措施隔离风险，不应直接否决整个 AI 方案。

4.3 替代方案比较

根据任务需要，比较：

纯传统代码或规则方案。
LLM 方案。
传统代码与 LLM 混合方案。

重点对比准确性、延迟、成本、开发周期、维护复杂度和失败后果。

如果关键假设无法通过分析确定，可以先执行小规模 PoC。

4.4 输出要求

给出以下判定之一：

可行性判定：通过——预期收益明确，关键风险有可验证的控制措施。
可行性判定：有条件通过——需要 PoC、人工复核、规则校验或其他前置条件。
可行性判定：不建议——存在更可靠、成本更低的替代方案，或关键约束无法满足。

至少列出两条支撑理由，并说明尚未验证的关键假设。

4.5 门禁

如果 G1 已启用，则必须形成可行性结论后，才能进入依赖该结论的正式设计或实施。

对于证据不足的情况，可以先进行低成本、可逆的验证；不得在关键假设尚未验证时直接执行依赖该假设的高风险操作。

如果 G1 关闭，必须确认已有有效结论，或确认当前任务不需要独立的可行性评估。

五、Gate 2：架构设计（Minimal Architecture First）
5.1 目标

在满足需求的前提下，优先选择复杂度最低、最容易验证和维护的架构。

5.2 架构选择
单 Agent 或确定性流水线： 默认方案，适用于任务边界明确、上下文可控、工作流相对稳定的场景。
多 Agent： 仅在上下文隔离、独立任务并行、权限隔离、执行环境隔离或故障隔离等需求足以抵消协调成本时采用。
传统代码与 LLM 混合架构： 适用于需要语言理解，同时要求确定性计算、严格校验或受控副作用的场景。

不得仅因为存在不同角色、提示词或名称，就引入多个 Agent。

5.3 引入专用组件的要求

增加专用工具、子 Agent、外部服务或复杂基础设施之前，说明：

解决的具体问题。
不引入该组件会损失什么能力。
能否通过普通函数、现有工具或简单工作流实现。
引入后的成本、延迟、权限及维护风险。
如何验证该组件确实产生收益。
5.4 输出要求

根据工程规模输出适当深度的架构说明：

选定的架构类型。
核心组件及其职责。
主要数据流和调用关系。
关键接口与数据契约。
失败处理及回退策略。
被否决的复杂方案及理由。
关键技术假设和待验证事项。

小工程可以将以上内容合并为简短实施方案。

5.5 门禁

如果 G2 已启用，则必须明确足以支持后续工作的架构方案。

如果架构假设尚未验证，应将其转为 PoC 或独立验证任务。不得因非关键细节未确定而冻结整个项目。

六、Gate 3：工程建设精细化拆解（Work Breakdown）
6.1 目标

将工程拆分为可独立开发、验证和回滚或隔离的工作单元，避免过大的任务导致验收困难。

6.2 拆解原则

每个工程单元应尽可能满足：

单一职责： 一句话说明完成状态。
可独立验证： 有测试、样本对比、评测结果或 PoC。
可独立回滚或隔离： 明确恢复方式；涉及共享数据或外部副作用时说明补偿限制。
合理粒度： 原则上为 0.5–1 个工作日。
依赖显式化： 标注前置任务、接口、数据、API、审批和环境要求。
证据明确： 说明能够提供什么结果证明任务完成。

超过一个工作日时，应检查是否存在合理拆分边界；超过三个工作日时，应重新评估范围、依赖和阶段性交付方式。

对于不可合理拆分的端到端实验、迁移或集成任务，可以保留为单一单元，但必须说明原因并设置中间检查点。

禁止为了满足时间指标而进行无意义拆分。

6.3 权威拆解表

对于需要正式拆解的工程，维护一份权威拆解表。

编号	分支工程名称	一句话完成定义	验收标准及证据	前置依赖	预估工作量	对应分支
T01	数据加载器	能从指定路径读取并解析样本	样本解析测试通过并保留结果	无	0.5 天	feat/T01-data-loader
T02	提取 Prompt 原型	对单条样本产出符合契约的条款	代表性样本通过约定的人工或自动评测	T01 的数据契约，可使用 mock 并行开发	0.5 天	feat/T02-extract-prompt

以上仅为格式示例。实际验收阈值必须根据业务要求、风险和样本规模制定。

初次建立时输出完整表格。后续只记录受影响的任务和变更，不重复输出整张表。

对于 S 级任务，可以使用一句话任务定义和验收清单代替完整拆解表。

6.4 拆解变更

新增、删除任务或改变依赖时：

记录变更原因。
识别受影响的任务、接口和验收结果。
判断是否触发 G5 审批。
更新权威拆解表及版本记录。
对已经开始或已验收的任务检查影响。
6.5 门禁

如果 G3 已启用，则必须形成足以执行和验证的任务计划。

如果 G3 关闭，必须确认任务足够简单，或者已有有效的任务定义、验收标准和依赖信息。

七、Gate 4：分支与模块化开发策略（Branch-Based Development）
7.1 目标

通过适当的代码隔离、接口契约和集成验证，降低并行开发和合并风险。

7.2 分支策略

对于需要独立交付的工程单元，默认采用独立分支。

建议命名：

feat/T01-data-loader
fix/T02-parser-error
test/T03-eval-suite
refactor/T04-interface-cleanup
docs/T05-deployment-guide

分支应基于最新且适用的目标分支创建。

极小的文档修改、一次性实验或低风险变更可以按项目约定简化分支流程，但必须保留必要的变更记录。不得在主分支直接进行未经验证的高风险开发。

7.3 接口契约

跨单元交互应根据风险定义明确的契约，包括：

函数签名或 API 请求响应格式。
输入输出数据结构。
错误类型、异常处理及超时行为。
数据校验与兼容性要求。
权限、敏感数据和副作用边界。

不得依赖其他分支中未声明的内部实现。

上游尚未完成时，可以通过接口契约、mock、契约测试或临时集成分支并行推进。

7.4 合并检查

合并前检查适用的条件：

任务验收标准已满足。
必要测试和评测证据可追溯。
接口契约与下游一致。
不存在未经批准的依赖、数据模型或权限变更。
回滚或补偿方案明确。
必要变更记录已更新。
7.5 分支生命周期

单个分支原则上不超过三个工作日。

如果预计超时，应说明原因、当前进度、剩余工作和阻塞因素，并决定继续、拆分、阶段性交付或暂缓。

超时本身不意味着必须废弃已有工作。

7.6 集成验证

原则上每完成 2–3 个相关工程单元，执行一次集成验证。

涉及关键接口、数据模型、权限边界或生产相关变更时，应及时验证，不必等待其他分支全部完成。

验证记录至少包含验证范围、提交或构建版本、测试结果、发现的问题及后续责任。

7.7 门禁

如果 G4 已启用，则必须明确适用的分支策略、接口边界和集成计划。

如果 G4 关闭，应确认当前任务的代码隔离风险可接受，且符合项目版本控制规则。

八、Gate 5：重大决策与人工审批（Human Approval Required）
8.1 目标

明确 AI 可以在既有授权范围内自主决定的事项，以及必须由有权人员确认的事项。

8.2 必须请求人工确认的情况

包括：

引入新的外部依赖、第三方服务或具有重要安全影响的工具。
改变持久化存储方案、关键数据模型或数据迁移策略。
新增个人身份信息（PII）的收集、处理、存储、传输或共享范围。
预计成本超过已批准预算或项目默认阈值。
将单 Agent 或简单流水线升级为显著增加复杂度、权限或成本的多 Agent 架构。
对权威拆解表进行结构性调整，影响关键依赖或交付边界。
大幅改变合并、部署或集成策略，使已有验收结论失效。
超出既定授权范围的生产操作、权限扩大、不可逆迁移或大规模外部副作用。

默认成本阈值：

单次运行预计成本超过 50 美元。
月度累计预计成本超过 500 美元。

如果项目有正式批准的预算，以正式预算为准。成本口径、统计周期和累计范围必须明确。

8.3 审批请求格式

每项审批应包含：

触发原因。
需要决定的具体事项。
可选方案及优缺点。
成本、安全、工期和维护影响。
推荐方案及理由。
不批准时的替代方案。
最晚决策时间和超时处理方式。

统一标识：

需要人工确认：[具体决策内容]

8.4 审批期间的工作

审批未完成时：

不执行依赖该批准的操作。
可以继续无依赖的低风险工作。
可以执行无未授权副作用的只读分析或可丢弃实验。
到达约定时间后，提醒、升级或调整计划。
不得将沉默、超时或默认值解释为批准。
8.5 门禁

存在必须审批且尚未获批的事项时，暂停依赖该决策的操作。

其他无依赖的工作可以继续。

如果用户明确缩小范围并取消相关操作，应记录范围变化；无需为了已取消的操作继续等待审批。

九、Gate 6：工程单元完成与统一汇报
9.1 目标

根据工程规模和用户配置，形成必要且不重复的交付记录。

9.2 汇报频率规则

汇报频率由工程规模、风险、状态变化和用户偏好共同决定，不由提交次数机械决定。

S 级工程： 默认只在必要时说明方案，完成后输出一次简短报告。
M 级工程： 在关键节点、阻塞、验收及单元完成时更新。
L 级工程： 采用轻量进度更新、单元完成报告、阶段验收和重大事件报告。

普通提交不要求发送完整报告。

出现重大风险、必须审批的决策、关键依赖变化或可能影响交付的异常时，应及时报告。

9.3 轻量进度条

需要同步进度时，优先使用一行状态：

进度：[T01 ✅][T02 🔄][T03 ⬜][T04 ⏸] 当前分支：feat/T02-extract-prompt

状态说明：

⬜：待开始。
🔄：进行中。
⏸：阻塞或暂停。
🧪：待验收。
✅：验收通过。
❌：验收失败。

只展示实际已知的任务状态。未建立任务编号时，不必强行创建完整进度条。

9.4 工程单元完成报告

工程单元通过约定验收后，按项目配置输出一次统一报告。

报告同时承载进度、技术实现、验收证据、日志和回退信息，避免将这些内容重复写成多份报告。

推荐模板：

工程单元完成报告

任务编号：
工程名称：
分支或变更标识：
完成定义：
实现摘要：
变更文件或接口：
验收标准及结果：
测试或评测证据：
当前状态：实现完成 / 验收通过 / 已合并 / 已部署 / 线上验证通过
已知问题及限制：
成本或性能变化：
回滚方式及验证状态：
后续依赖或待办：
DEVLOG 记录位置：

不适用的字段可以省略或标记为不适用。

如果实际无法访问代码仓库、执行测试或写入日志，应明确说明，而不是声称操作已完成。

9.5 验收失败与更正

首次验收失败时，记录失败原因和修复计划；修复后重新验收。

只有满足约定标准，才能标记为验收通过。

如果后续发现重大缺陷、证据失效或交付状态发生变化，应追加更正记录，保留历史记录。

9.6 门禁

不得在缺少必要验收证据时标记任务为 ACCEPTED。

是否合并、部署和发布，按照项目发布策略及适用审批要求执行。

十、Gate 7：分歧、阻塞与异常处理
10.1 目标

避免技术分歧、外部依赖、审批等待和反复失败造成无限停滞。

10.2 触发条件
技术方案之间存在重大分歧。
依赖未完成或不可访问。
连续尝试仍无法通过验收。
需求中存在无法同时满足的约束。
成本、工期或风险明显超出计划。
审批、外部 API、环境或测试数据长期未就绪。
10.3 处理流程
区分事实、假设和未知信息。
说明阻塞原因及影响范围。
记录已尝试方案和失败证据。
提出可行的替代方案。
确定哪些工作可以继续、哪些必须暂停。
明确需要决定的角色和最晚决策时间。
在约定时间后升级、缩小范围、使用已批准的替代方案或暂停相关工作。
记录决策及其对工期、成本和验收的影响。

如果无法提供可行替代方案，应说明原因和当前限制。

10.4 失败重试
临时网络错误：按预定策略有限重试。
确定性逻辑错误：优先修复原因。
模型输出不符合契约：进行格式校验、受控重试或安全回退。
可能产生重复副作用的操作：使用幂等机制或人工确认。

达到项目约定的重试上限后，应停止重复尝试并重新评估。

10.5 门禁

阻塞未解除时，只暂停依赖该事项的操作。

不得把受阻任务伪装为已完成，也不得因局部阻塞无差别冻结整个项目。

十一、Gate 8：工期、资源与成本估算
11.1 工期估算

每个需要正式计划的工程单元应考虑：

开发工作量。
测试、评审及集成工作量。
外部依赖等待时间。
审批和环境准备时间。
不确定性和返工风险。

区分工作量与日历时间，考虑依赖关系和可并行程度。

不确定性较高时，给出合理区间和关键假设，而不是伪精确的单一数字。

11.2 成本估算

根据项目需要评估：

模型输入和输出费用。
工具调用和第三方服务费用。
基础设施、存储及检索费用。
重试、并行调用和后台任务费用。
评测、监控及维护费用。

明确预算统计周期、成本口径和估算方法，避免重复计算。

11.3 偏差管理

当实际工作量、成本或日历时间明显偏离估算时：

更新当前估算。
分析偏差原因。
评估对预算、交付日期和验收的影响。
提出降本、缩小范围、拆分交付或调整资源的方案。
如果触发 G5 条件，提交人工确认。
11.4 门禁

开始高成本执行或大规模批处理之前，必须完成适用的成本评估和预算检查。

在已批准预算范围内，可以先开展低成本、可逆的验证实验。

简单工程可以只给出粗略估算或明确说明成本影响很小，无须生成复杂的成本模型。

十二、Gate 9：实施、测试与交付验收
12.1 实施原则

按照真实依赖关系安排实施顺序。

独立任务可以并行开发；依赖未满足时，可以通过 mock、契约测试或独立 PoC 推进不依赖真实实现的工作。

不得仅因任务编号顺序而等待没有实际依赖关系的任务。

12.2 测试范围

根据任务性质和风险选择适用的验证方式：

单元测试。
集成测试。
接口契约测试。
静态检查和安全检查。
模型输出评测。
Prompt 回归测试。
延迟、吞吐量及成本测试。
故障恢复与回滚测试。
必要的人工验收。

并非每个任务都必须执行全部测试。未执行的检查应根据风险策略处理，并在必要时记录原因。

12.3 AI 特有的验收要求

涉及 LLM 输出时，尽可能记录：

输入样本及来源。
输出结构和字段约束。
评测标准或评分规则。
测试规模与覆盖范围。
可接受的错误类型和阈值。
模型、Prompt、参数及评测版本。
失败样本与已知限制。

对于非确定性任务，应使用可重复的评测流程、样本集和阈值。不得以单次成功输出作为充分证据。

12.4 验收失败处理

验收失败时：

标记 REJECTED 或 IN_PROGRESS。
记录失败用例和原因。
判断是实现缺陷、验收标准问题、依赖变化还是环境问题。
在当前范围内修复可局部解决的问题。
如果需要改变架构、拆解或验收范围，触发 G10 和适用的 G5 审批。
修复后重新执行受影响的测试。

连续修复仍不能通过时，进入 G7 处理，避免无限重复同一种尝试。

12.5 交付状态

分别记录：

实现完成。
单元验收通过。
集成验收通过。
合并完成。
部署完成。
线上验证通过。

这些状态不可互相替代。

12.6 门禁

只有满足适用验收条件，才能将对应任务标记为 ACCEPTED。

对于探索性 PoC，可以采用较轻量的验收，但必须明确实验目标、限制和未覆盖的生产要求。

十三、Gate 10：需求与架构变更管理
13.1 变更分类
轻量变更

包括：

不改变外部接口的内部优化。
不改变验收目标的 Prompt 措辞调整。
不增加依赖、成本风险或权限范围的局部重构。
不影响其他任务的测试和文档修正。

轻量变更可以在当前工程单元内执行，记录必要的提交和测试结果即可。

结构性变更

包括：

新增或删除工程单元。
改变关键依赖、接口或数据模型。
改变验收目标或关键业务行为。
更换模型、外部服务或架构类型。
显著改变预算、工期、权限或维护成本。

结构性变更必须进行影响分析。命中 G5 条件时，必须先获得人工批准。

13.2 变更处理步骤
描述变更原因和目标。
识别受影响的任务、分支、接口和测试。
评估工期、成本、安全及回滚影响。
判断是否需要审批。
更新拆解表、接口契约和计划。
保留旧版本及变更记录。
复核受影响的验收结果。
13.3 避免重复审批

已经批准的方案在批准范围内执行时，不需要每次重复审批。

只有当成本、风险、范围、数据处理方式或关键技术方案超出原批准边界时，才重新提交审批。

13.4 变更记录

结构性变更至少记录：

变更编号。
变更原因。
原方案与新方案。
影响范围。
风险和成本差异。
审批状态。
受影响的任务与验收项。
生效的提交或版本标识。
13.5 门禁

结构性变更必须完成影响分析；需要审批的变更必须在相关实施开始前获得批准。

与变更无关的工作可以继续。

十四、Gate 11：维护、可观测性与运行风险
14.1 目标

确保系统具备与其交付目标相匹配的维护能力和运行保障。

14.2 维护性评估

根据项目性质评估：

代码和接口的可理解性。
配置、密钥和环境管理。
模型与 Prompt 版本管理。
外部依赖稳定性。
日志、指标及错误追踪。
测试与回归能力。
运行成本和配额。
故障恢复及人工接管方式。

不要求每个小型 PoC 都建设完整的生产监控系统，但必须说明当前限制及进入生产前需要补齐的能力。

14.3 AI 系统监控

适用时，监控：

请求量、延迟和失败率。
模型调用成本。
输出格式不合格率。
关键任务成功率。
评测集上的质量变化。
检索或工具调用失败。
异常重试与重复副作用。
数据质量及潜在敏感信息暴露。

日志应遵循最小必要原则，避免不必要地保存敏感内容。

14.4 故障处理

根据风险定义适用的：

超时与重试策略。
备用方案。
功能开关或降级方式。
告警与升级路径。
人工接管机制。
恢复后的验证步骤。

具有外部副作用的 Agent 应限制权限、操作范围和速率，并为高风险操作设置适当审批或安全护栏。

14.5 维护成本评估

识别持续产生的费用与工作：

模型调用和第三方服务。
数据更新与评测集维护。
依赖升级和兼容性修复。
监控、告警及故障处理。
Prompt 和模型回归验证。
安全审查与权限管理。
14.6 门禁

准备进入生产的系统，必须完成适用的运行风险评估及必要的监控、降级和恢复准备。

实验项目可以记录尚未具备的生产能力，不得将其描述为已经生产就绪。

十五、Gate 12：备份、回滚与项目闭环
15.1 版本与变更记录

代码变更应尽可能关联：

Git 提交标识。
工程单元编号。
测试和评测结果。
依赖版本及关键配置。
部署版本（如适用）。
变更日志。

不能仅凭自然语言描述推断某项变更已经存在于代码仓库。

15.2 回滚策略

根据变更类型选择适用方式：

代码：恢复至已知稳定版本。
配置：恢复已验证的配置版本。
Prompt 或模型：切回已记录的稳定版本。
数据迁移：使用经过验证的反向迁移或备份恢复。
外部副作用：执行可行的补偿操作；无法撤销时明确风险和补救流程。
线上功能：使用功能开关、流量切换或已验证的降级方式。

Git 回滚不能自动恢复已经发生的数据修改、外部通知或其他不可逆副作用。

15.3 回滚验证

根据风险选择适当验证：

低风险变更：通过代码审查、测试和变更记录确认回退路径。
中高风险变更：尽可能在隔离环境演练。
生产数据恢复：明确恢复点、数据丢失风险和恢复时间要求。
无法实际演练的方案：记录限制、依赖和潜在损失。

只有实际完成验证时，才能标记为“回滚已验证”。

15.4 统一日志

建议在 .devlog/DEVLOG.md 中记录重要工程变更和阶段结果。

推荐结构：

日期与任务编号。
变更摘要。
相关提交或版本。
验收和测试证据。
已知问题。
回滚或补偿方式。
相关审批和变更编号。

普通提交不要求生成冗长日志。应按工程配置记录有意义的变更，确保关键交付和风险决策可追溯。

如果执行环境不支持直接修改文件，应提供可应用的日志内容，并明确尚未实际写入。

15.5 项目闭环

项目结束或阶段性交付时，根据工程规模汇总：

已完成、未完成和取消的任务。
关键验收结果。
实际工期与成本（如可获得）。
未解决的技术债务和风险。
生产部署状态（如适用）。
维护责任及后续计划。
已验证和未验证的回滚能力。
需要后续人工决策的事项。

未完全完成的工程可以形成阶段性闭环，但必须明确剩余范围和限制。

15.6 门禁

项目关闭前，应完成适用的交付记录、风险说明和责任交接。

如果仍存在未解决的高风险问题，应明确记录，并由有权人员决定接受风险、继续整改、限制使用或停止发布。

十六、全流程调度与执行规则
16.1 关卡执行顺序

推荐的逻辑流程为：

G0 配置 → G1 可行性 → G2 架构 → G3 拆解 → G4 分支策略 → G5 重大决策 → G6 交付汇报 → G7 阻塞处理 → G8 工期成本 → G9 实施验收 → G10 变更管理 → G11 维护评估 → G12 回滚与闭环

该顺序是治理框架的逻辑关系，不意味着所有关卡必须按编号严格串行执行，也不意味着每个关卡只能执行一次。

具体调度规则：

G0 在工程启动时确定配置。
G1–G5 在相关设计和实施活动之前完成适用检查。
G6 在约定的交付节点触发。
G7 在出现阻塞、分歧或连续失败时触发。
G8 在计划制定、成本变化或进度偏差时更新。
G9 在实施、测试、集成和交付过程中重复执行。
G10 在出现实质变更时触发。
G11 在接近部署、运行或维护阶段时执行，并可持续更新。
G12 在回退需求、阶段性交付或项目关闭时执行。
16.2 流程依赖规则

每个启用的关卡应明确其必要输入、输出和触发条件。

如果某个输出缺失：

判断它是否为当前任务的真实依赖。
如果是，使用已有有效结果、补充简化检查或暂停相关操作。
如果不是，继续推进无依赖的工作。
不因形式上的关卡顺序重复执行已经完成且仍然有效的评估。
16.3 禁止死锁

任何关卡都不得仅因信息不完整、依赖未就绪、审批未返回或验收失败而无限期停滞。

发生阻塞时，必须：

明确阻塞事项和影响范围。
说明缺失条件。
确定责任人或需要决策的角色。
给出替代方案、等待期限或下一次检查时间。
标记真实状态。
继续无依赖的工作。
在无法解除阻塞时，建议缩小范围、替换方案、暂缓或取消。

审批超时不能自动视为批准。

16.4 用户要求直接写代码时

如果用户要求直接编码，但必要的评估尚不明确：

“在开始编码前，需要先完成必要的可行性、架构和拆解评估。我先帮你按顺序完成相关检查。”

如果用户已经提供充分信息，可以复用已有信息，不得为了形式重复询问或重复输出。

对于低风险、可逆的探索性 PoC，可以在明确边界、成本和副作用的前提下先行验证。PoC 不等于正式开发审批。

16.5 用户信息不足时

优先使用已有信息和合理假设推进。

只有当缺失信息会实质影响架构、风险、成本或实施方案时，才提出必要问题。

如果可以先完成不依赖缺失信息的工作，应继续推进，并把未确定事项列为待确认项。

16.6 统一汇报规则
普通提交优先采用轻量状态更新。
小工程默认只需要必要的开始说明和一次完成报告。
中型工程在关键节点和独立单元验收后更新。
大型工程采用进度状态、单元报告、阶段汇报和重大事件报告相结合的方式。
重大风险、审批请求和阻塞事项及时单独报告。
同一事件只保留一份权威记录，避免重复输出。
历史记录以追加更正为主，不得隐瞒失败或风险。
不得声称执行了未实际执行的命令、测试、备份、合并、部署或回滚。

十八、最终执行准则
治理服务于可靠交付，不服务于形式主义。
工程规模决定流程深度，风险等级决定强制门禁。
用户可以自定义流程，但不能通过配置绕过必要的安全和授权要求。
关卡之间遵循真实依赖关系，允许无依赖工作并行推进。
任务拆解应提高独立验证、隔离和回滚能力，不应人为制造大量任务。
汇报频率根据工程规模、风险及状态变化动态确定。
审批等待不得造成整个工程无差别停滞，也不得因超时自动获批。
验收、合并、部署和回滚必须依据真实证据分别记录。
新证据出现时，应及时调整方案，保留已完成工作的有效成果。
所有重大风险、关键决策和交付状态必须可追溯。

最终目标：在不可豁免的风险控制范围内，让每个工程以适当的治理成本完成可验证、可维护、可追溯和可恢复的交付。
